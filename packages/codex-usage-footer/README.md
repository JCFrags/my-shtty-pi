# Codex Usage Footer

- Purpose: Show shared Codex usage and the unofficial Tibo Button reset forecast in the Pi footer and through `/codex-usage`.
- Status: active canonical
- Pi entrypoint: `extensions/codex-usage-footer.ts`
- Load form: source-loaded
- Test command: `npm test --workspace packages/codex-usage-footer` is not used because this package is not a root workspace; run `npm --prefix packages/codex-usage-footer test`.
- Repository verification: stage the intended files, then run `npm run verify -- --product codex-usage-footer` from the repository root. Verification reads Git index blobs, not unstaged worktree files.

## Shared quota behavior

An upgraded interactive or RPC Pi instance using the built-in `openai-codex` provider with OAuth participates in one account-isolated cache. Ordinary OpenAI API-key sessions do not poll the ChatGPT account endpoint. The extension uses Pi's resolved provider authentication API, which refreshes OAuth when needed; it never reads `auth.json` directly and never writes a token or account ID to the cache.

The cache is under `${XDG_CACHE_HOME}/pi/codex-usage/` when `XDG_CACHE_HOME` is absolute, otherwise `~/.cache/pi/codex-usage/`. Account IDs are SHA-256 hashed for quota file names and cache keys. Banked-reset details use an account-scoped companion cache and route-specific GET lock. This separation is required during mixed-version operation: an older usage-only client refreshes the usage gate and rewrites the main cache without preserving fields it does not know. It therefore cannot reserve or erase the companion state. On first use, an upgraded client copies valid banked fields and their request timestamps from the main cache into the companion without making an early request. The public forecast uses one separate `tibo-button-forecast.json` file shared by all Pi clients for the same OS user. It is not account-scoped. The directory is mode `0700`, cache files are mode `0600`, and publication uses a temporary file plus atomic rename. Each route has an atomic directory lock. A lock older than 45 seconds can be atomically taken over, so a crashed polling process does not stop later polling.

Participating processes watch both account cache files and also scan every five seconds as a portable fallback. By default, one process performs the authenticated `GET https://chatgpt.com/backend-api/wham/usage` read and one process performs the read-only `GET https://chatgpt.com/backend-api/wham/rate-limit-reset-credits` details read at most once per 180-second account interval, and history retains 64 snapshots. Each route persists its shared attempt gate before network I/O, so another upgraded process or a reload does not multiply requests. An older process can continue to own the usage route without starving the banked-details route. Authenticated requests reject redirects, never send the reserve opt-in header, and have no consume or reset action. `/codex-usage` Shared settings offers bounded polling choices of 60, 180, 300, or 600 seconds and history limits of 16, 32, 64, or 128. Changes are account-scoped, lock-coordinated, and delivered to all upgraded local processes for the same account. Menu writes wait for bounded lock retries and report a failure in the UI. Independent display fields are patched against the latest value under the lock, so concurrent edits do not replace each other with stale copies. Normal Codex response quota headers append a shared snapshot but do not defer the full poll interval. Failed reads and invalid cache/configuration data preserve the last good in-memory snapshot and settings.

`/codex-usage` opens a keyboard menu. Use Up and Down arrows to navigate, Enter to select, and Escape to return or close. The menu contains Usage details, Banked resets, Recent history, Display settings, Tibo Button Forecast, and Shared settings. Banked resets shows the summary count source and freshness, details freshness, and each returned available credit's type, status, granted time, expiry, title, and description when supplied. It never displays or caches credit IDs. The forecast screen links to the source and shows its unofficial, uncalibrated 48-hour scope, source and local fetch times, ages, next eligible check, staleness, and the last refresh failure when applicable. Usage details shows the current snapshot. Recent history shows up to 12 newest entries from the configured bounded history.

Display settings contains Display scope, Show footer, Standard Codex, Spark, Banked resets, Tibo Button Forecast, Usage format, and Reset format. The Banked resets submenu controls the count and next known expiry independently. Both fields default on and follow the selected shared or session display scope. The forecast defaults on and follows the same shared-by-default or session-only display scope. It also follows the overall footer switch. The forecast can remain visible when every quota usage/reset field is off. The Standard Codex and Spark submenus each contain independent Weekly usage, Weekly reset, 5-hour usage, and 5-hour reset controls. Standard weekly fields default on. Standard 5-hour and all Spark fields default off. A missing duration class reads `Not reported`; it never reads zero or unlimited. A semicolon separates windows, and a middle dot separates enabled fields inside one window.

Display scope defaults to All local sessions. Shared display preferences are account-scoped and use the same atomic file and watcher delivery as polling settings. Switching to This session copies the current shared display once, then persists later overrides in that Pi session branch. Switching back shows shared values without deleting the session overrides; switching to This session again restores them. Thus, a scope switch never silently overwrites either set.

The footer classifies a window as Weekly only when the returned duration is exactly 604,800 seconds, or 5-hour only when it is exactly 18,000 seconds. Header durations in minutes are converted to seconds without rounding. It never uses primary/secondary position, plan name, countdown, or reset distance. The default footer therefore shows only a reported Standard Codex weekly window, for example `Weekly 19% remaining · resets Tue at 18:21 (in 4d 3h)`. Spark is a separate returned family and keeps its own windows and controls.

History records preserve the returned family identity, optional family name, raw primary/secondary slot, exact duration, usage, reset, and per-field observation times. Partial headers merge by family ID and raw window slot. Unreported families and fields remain available with their prior observation times instead of disappearing or becoming falsely fresh. Details identify carried fields, and the compact footer marks displayed carried values as stale. Existing version-1 records without duration remain readable as `Unknown duration`; the extension does not infer a duration. Details and history retain unknown durations and other additional families, but unknown classes do not appear in the compact footer.

Reset times use the machine's local time zone and 24-hour clock. Friendly formats use `today`, `tomorrow`, or a three-letter English weekday. Detailed screens add the date and current local time-zone abbreviation. A timestamp that is due or past remains `reset due, awaiting update`; the extension does not infer a refresh from time passage. The five-second cache scan also refreshes countdown text without an extra API request.

## Public Tibo Button forecast

When at least one visible Codex footer has the forecast enabled, upgraded clients coordinate one unauthenticated public `GET https://www.willcodexquotareset.com/api/forecast`. In shared display scope, the client first loads the persisted account display preference. A saved off choice cannot transiently render or start the forecast. Explicit session preferences can participate without waiting for shared preferences. The request sends no Codex credentials, cookies, account IDs, or private data. It refuses redirects, times out after 10 seconds, and reads at most 128 KiB. It retains only validated forecast fields plus local scheduling and freshness timestamps, not source incidents, posts, or other bulk response data.

The first participating client checks once when no cache exists. Under the shared lock, it atomically reserves and persists the attempt and a next-attempt time before network I/O. A crash, abort, disable, or restart therefore cannot repeat the request inside the gate. Later checks are never eligible faster than 30 minutes after the prior attempt. After a valid response, scheduling aims for 15 minutes after the source's reported cycle, repeated in 30-minute phases, while preserving the minimum interval. The source page says it checks sources every 30 minutes, but this does not prove an exact refresh schedule. Client startup, suspension, contention, failures, the 30-minute minimum gate, and source timing can produce 30-to-60-minute check gaps. A 15-minute maximum lag or freshness guarantee does not exist. Invalid, stale, or future source timestamps use a bounded 30-minute fallback and never cause rapid retries.

The compact text is `Tibo Button Forecast: <score>% <headline>`, for example `Tibo Button Forecast: 23% Probably not today.` The headline is derived only from the validated server fields and the documented source-page thresholds. The extension does not predict its own score. A source timestamp older than two hours is labeled stale. Oversized responses and aborted or timed-out streams are actively canceled. A malformed, oversized, timed-out, or failed response never appears current; the last valid forecast remains visible with an honest failure marker, or the forecast is unavailable.

This forecast is third-party and unofficial. It has a 48-hour horizon and reports `calibrated: false`. It never changes quota counters, reset times, or quota history.

## Limitations and upgrades

- Existing Pi processes that loaded an older extension do not gain this watcher automatically. Reload or restart each process so it becomes a participating upgraded instance.
- Cross-process delivery is file based and can take up to five seconds when native file watching is unavailable.
- The usage route and payload are backend contracts used by the current official OpenAI Codex client, not a versioned public OpenAI API. Official `openai/codex` source at `ddea03ad049142943bdbf13e937b1d67e8c1ba0c` reads standard `rate_limit`, and reads named families from `additional_rate_limits` entries with `limit_name`, `metered_feature`, and `rate_limit`. Each family can contain primary and secondary windows with `limit_window_seconds`. This extension recognizes Spark only when a returned additional entry has `limit_name` equal to Spark, case-insensitively. Recheck this finite contract before a future upgrade.
- Version-1 positional display preferences migrate only `Show footer`, Usage format, and Reset format. Positional usage/reset toggles are not mapped to durations or Spark. New duration controls use the documented defaults. The live cache had no saved display preference at preparation time, so this migration did not overwrite a current shared choice.
- The usage summary supplies the banked reset count when present. Missing summary metadata preserves the prior count and its original observation time; it does not turn unknown into zero. The newest valid summary or details count is authoritative; the usage summary wins an equal-time tie. The extension validates a returned usage `account_id` before it accepts either quota or summary data.
- The details response can return fewer credit records than `available_count`. The footer says `next known/listed expiry` unless the details match the newest authoritative count and every available credit has a known future expiry. Null or invalid expiry data is Unknown, not unlimited. Expired timestamps remain expired or due and never imply a reset.
- Summary and details failures are independent. A details failure preserves the last good details with its own stale marker and does not suppress fresh quota or count data. Responses are bounded to 256 KiB, and externally supplied title and description text is stripped of terminal controls and length-limited.
- The extension performs only passive GET requests. It does not send the reserve opt-in header, consume a reset credit, or expose any POST reset action.
